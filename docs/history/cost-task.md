# Task: measured cost & resources per stage, shown beautifully

Context: a knowledge assistant over a crawled Everstake corpus (test assignment for an AI Automation Lead role). Assignment §5.6 demands *measured* costs, not estimates: tokens to build the index, its cost, the cost of one query, and a ×50 extrapolation with the arithmetic shown. We want to go beyond that and make cost/resources a first-class, visible part of the product: every stage, every question, every step — money, tokens, model, time, CPU, memory — and present it so that a non-engineer understands it in ten seconds.

## What to build

1. **Accounting.** One place where each pipeline stage run is recorded (crawl, dedup, chunk/index, embeddings, fact extraction, eval, and each single question): start/end, wall time, CPU time (`process.cpuUsage` / `resource.getrusage`), peak RSS, items processed (documents/chunks/questions), bytes downloaded, tokens in/out/cached, USD, model, provider. Token counts must come from the providers' usage fields (Gemini `usageMetadata`, OpenAI `usage`), never from estimates; USD = tokens × a price table kept in config with the date the prices were copied. Stages with no model calls (crawl, dedup) cost $0 but still record time/CPU/RAM/bytes. For a question, record every step: query embedding, each model turn (tokens, cache hits, $), each tool/code step (ms, $0). Past runs that already have model-call logs should be aggregated into the new structure where possible; where time/CPU cannot be recovered, say so — do not invent.

2. **`COST.md`, generated by a command** (`npm run cost` / `make cost` or similar), committed to the repo: (a) table per stage: what runs (code vs model), model, units, tokens in/out (cache), $, wall time, CPU, peak RAM, $ per unit; (b) one real question broken down step by step with tokens/$/ms per step and the total; (c) the ×50 extrapolation *per row*, with the formula next to each number and an explicit list of what is measured vs assumed (prices after a date, other hardware, parallelism); (d) a short "where the money goes" sentence (e.g. "98% of index cost is fact extraction; 90% of index time is polite crawling"). State which machine measured what (dev laptop vs the VPS).

3. **In the UI — a dedicated "Cost" view/menu**, designed to impress and to be understood instantly: a headline ("Building the whole index cost $2.19. One question costs about a cent."), stacked bars for money and time by stage, the stage table, and each stage expandable into its individual runs. Plus, on every answer, the pipeline summary line becomes an expandable **receipt**: step → tool or model → tokens (cache) → $ → ms, with the total. Plain language everywhere ("Reading the fact ledger — code, free, 5 ms"; "Model turn 2 — gemini-3.8-flash, 4 900 tokens in (2 000 cached), 60 out, $0.004"). Keep the existing visual language of the app (fonts, accent, both themes) — this must look like part of the product, not a bolted-on dashboard.

4. **Docs.** A paragraph in REPORT.md §3 pointing at COST.md and explaining the method (what is measured, how, what is assumed). README: the command.

## Constraints

- Models: Gemini 3.x only (`gemini-3.8-flash` for answers, `gemini-3.5-flash-lite` for cheap work). Never Gemini 2.5.
- Keep API spend for this task under ~$1 (a handful of questions to fill the receipts; re-running crawl/dedup is free and gives real time/CPU numbers — do it).
- Tests must pass; add tests for the accounting math (aggregation, price table, receipt totals equal the sum of steps).
- No new heavy dependencies. Code stays explainable line by line.
- Do not `git push`.
