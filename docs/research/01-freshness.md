# 01 — Актуальність даних: індекс, live fetch чи гібрид

## Рішення

**Гібрид, і він не «на всяк випадок», а тому що три класи питань мають різну ціну помилки.**

- **База з інкрементальним re-crawl** — основа. Індекс дає провенанс: snapshot із sha256, дата публікації, ланцюг редиректів. Без snapshot неможливо довести, звідки взялося число, а для переговорів на мільярди доказовість важливіша за свіжість на годину.
- **On-demand fetch** — вузький інструмент агента (`fetch_live_page`, allow-list із 3 доменів, уже є в `config/kb.yaml`). Викликається, коли (а) питання містить маркер часу («зараз», «сьогодні», «поточний»), (б) сторінка в індексі старша за свій SLA, (в) два джерела суперечать і різниця в датах < 30 днів.
- **Живі числа (APY, uptime, chains) — взагалі не з корпусу**, а з `mcp.everstake.com`. Ми вже виміряли: на маркетинговій сторінці `/mcp` надруковано 3.41% ETH APY, а `get_chains` того ж дня віддає 2.93%. Кешувати таке в індексі — гарантована брехня.

Чистий «Perplexity-стиль» (кожен запит = живий фетч) відпадає: він не вміє відповісти на «як змінилось позиціонування за два роки» — історії на живій сторінці немає. Чистий індекс відпадає на «яка ставка зараз».

## Порівняння трьох варіантів (числа наші, виміряні)

Базові виміри з `REPORT.md` / таблиці `llm_calls`: **441 канонічний документ, індекс = $2.19** ($0.044 embeddings + $2.141 fact extraction на Haiku 4.5), тобто **$0.005 за документ**. Доступно на доменах ~900 сторінок → повний індекс усього доступного ≈ **$4.5**. Запит: **$0.041** (Opus 5) / **$0.011** (Gemini 3.8 Flash), середня латентність **4 777 мс**.

| | A. Індекс + re-crawl | B. On-demand fetch | C. Гібрид (рекомендація) |
|---|---|---|---|
| Разова побудова | $2.19 (441 док) | $0 | $2.19 |
| Утримання/місяць | $0.30–$0.60 (див. нижче) | $0 | $0.30–$0.60 |
| Вартість запиту | $0.011–0.041 | $0.06–0.09 (+8–12k токенів сирої сторінки в промт) | $0.011–0.041 звичайний; $0.06–0.09 на ~10–15% запитів, що тригерять фетч |
| Латентність | 4.8 с | 7–10 с (DNS+TLS+HTML 0.3–0.9 с × 1–3 сторінки, більший промт) | 4.8 с / 7–10 с на фетчі |
| Довіра | **висока** — snapshot + sha256, відповідь відтворювана через рік | **низька** — сторінка може змінитись між відповіддю і перевіркою, нема що показати аудитору | висока; live-фрагмент позначений окремо і не входить у підписаний доказ |
| Історія / синтез | **так** — timeline у ledger (70 → 85 → 130+) | **ні** — жива сторінка не знає минулого | так |
| Прозорість для юзера | «станом на дату краулу» | «щойно з сайту» | обидві мітки в одній відповіді, різними бейджами |
| Головний ризик | протухання (кейс CEO) | prompt injection зі свіжої сторінки + недоказовість | складність: два шляхи довіри треба явно розділяти в UI й в audit log |

**Чому «недоказовість» — не абстракція.** Клієнт питає, скільки йому виплатити кешбеком. Через місяць сперечається. У варіанті A ми показуємо snapshot із хешем і датою. У варіанті B — «ну, тоді на сторінці було так».

## Схема re-crawl

```
                    ┌───────────────── scheduler (cron, по типу джерела) ────────────────┐
                    │                                                                    │
   sitemap.xml ─────┤ lastmod > last_seen ?  ──no──► skip (0 запитів, 0 $)                │
   (735 URL)        │        │yes                                                        │
                    │        ▼                                                           │
                    │  HEAD / GET з If-None-Match + If-Modified-Since                    │
                    │        │                                                           │
                    │   304 ─┴─► skip, оновити тільки checked_at                         │
                    │   200 ───► extract → sha256(normalised_text)                       │
                    │              │                                                     │
                    │   hash той самий ─► skip (косметична зміна: банер, лічильник)      │
                    │   hash інший ─────► enqueue(doc_id, reason=content_changed)        │
                    └───────────────────────────────┬────────────────────────────────────┘
                                                    ▼
                              черга (SQLite table `recrawl_queue`, пріоритет = tier × freshness_sla)
                                                    ▼
                    re-index документа: chunks → FTS5 → embeddings → fact extraction
                                                    ▼
                    diff фактів: (key, old_value, new_value, old_as_of, new_as_of)
                                                    ▼
                    якщо key ∈ watched_keys (ceo, networks, tvl, delegators, uptime, certifications)
                                → alert у Slack + рядок у `fact_changes`
```

Три сита економлять гроші саме в такому порядку: `lastmod` (0 HTTP-запитів на документ), умовний GET (запит без тіла), хеш контенту (тіло є, але переіндексації немає). На нашому корпусі це означає, що з 441 документа реально переіндексовуються одиниці на тиждень.

### Частота за типом джерела

| Джерело | Док. | SLA свіжості | Частота | Чому |
|---|---|---|---|---|
| Живі сторінки (`/company/about`, `/ai-info`, продуктові, `/mcp`) | ~40 | 1 год | щогодини (умовний GET) | тут живе кейс CEO: сторінка без дати, яка «описує теперішнє» |
| Блог / resources (everstake.com) | 250 | 24 год | щодня по sitemap `lastmod` | нові пости, старі майже не правляться |
| Прес-релізи, third-party | 7 канон. + 11 аліасів | 24 год | щодня, тільки нові URL | синдикація з'являється пачкою протягом доби |
| `docs.everstake.com` | 69 | 7 днів | щотижня через `llms.txt` | Markdown, змінюється релізами |
| GitHub org (README, `mcp/tools.yaml`) | 11 | 7 днів | щотижня (ETag від API) | ліміт API, зміни рідкісні |
| YouTube субтитри | 12 | 30 днів | щомісяця, тільки нові відео | ASR-транскрипт не переписується |
| Живі числа (APY, uptime, chains) | — | 0 | **не індексуються взагалі** | завжди через MCP у момент запиту |

**Вартість утримання.** Найгірший тиждень (переписали 10% корпусу): 44 док × $0.005 = **$0.22**. Реалістичний тиждень (2–3%): **$0.05–0.07**. Плюс ~3 500 умовних GET на тиждень — це трафік, не гроші. Тобто **менш як $1/місяць проти $2.19 за повний ре-індекс щоразу** — інкрементальність окупається з першого ж тижня, і на корпусі ×50 різниця стає $109 vs ~$3.

### Що робити зі змінами, а не лише детектувати

Detection без reconciliation безглузда. При зміні watched-факту пишемо в `fact_changes` рядок `(key, old, new, first_seen, source_url, snapshot_hash)` — і саме цей рядок дає відповідь «CEO змінився в червні 2025» замість того, щоб реконструювати це щоразу з дев'яти прес-копій. Кейс CEO у нас зараз вирішений правилом «жива сторінка станом на дату фетчу»; це правило **розпадається, щойно фетч застаріє**, тому re-crawl — не оптимізація, а умова коректності вже наявної логіки.

## Як «as of» показується користувачу

Одна відповідь може містити три різні за природою твердження, і вони не мають виглядати однаково:

```
Everstake підтримує 130+ мереж історично; активних ~30.        [as of 2026-09-11 · snapshot]
   ├─ [1] everstake.com/ai-info · published 2026-07-01 · crawled 2026-09-11 · sha256 4f2a…
   └─ [2] everstake.com/resources/blog/… · published 2026-04-14

APY Ethereum: 2.93%                                            [live · Everstake MCP · 12:41:07]
   └─ не з корпусу, не підписується, оновиться при наступному запиті
```

Правила UI:
1. **Бейдж кольором за природою джерела**: `snapshot` (є хеш, відтворюється) / `live fetch` (є час фетчу, не відтворюється) / `MCP live` (числа провайдера).
2. **Дві дати, не одна**: `published` (коли джерело це сказало) і `crawled` (коли ми це бачили). Плутанина між ними — це рівно та пастка, на якій 156 старих постів отримали `lastmod 2026` після міграції домену.
3. **Позначка протухання**: якщо `crawled` старший за SLA типу джерела, поруч з'являється «дані старші за N год, перевірити наживо» і кнопка, що змушує `fetch_live_page`.
4. **Питання без часу — відповідь без обіцянок**: на «хто CEO» ми не пишемо «зараз», ми пишемо «станом на 2026-09-11 за сторінкою компанії».

## Що показати на демо

1. `SELECT key, old_value, new_value, first_seen FROM fact_changes` — таблиця, де видно, як факт змінювався, і що система це помітила сама, без переіндексації всього.
2. Запустити re-crawl наживо: 441 URL → 437 `304 Not Modified` за ~20 секунд, 4 у черзі, вартість оновлення на екрані ($0.02).
3. Одне питання з маркером часу («яка ставка ETH зараз») → у pipeline-панелі видно, що агент **не** пішов у корпус, а викликав MCP, і відповідь має бейдж `live`.
4. Поруч — питання «як росла кількість мереж» → корпус + ledger, бейдж `snapshot`, три дати.
5. Показати штучно протухлий документ (підмінити `crawled_at` на -10 днів) і жовту плашку «перевірити наживо» в UI — тобто протухання видно ще до того, як хтось поскаржиться.
