# 05 — Як цей проєкт сам себе документує

## Рішення

**Звіт пише агент наприкінці сесії, з git log і результатів eval — а не людина з памʼяті.** Це не зручність, а перевірка тези з документа 04 на собі: якщо схема «агент реконструює день із машинних слідів, людина підписує» не працює для одного розробника й одного репозиторію, немає підстав продавати її операційному директору з чотирма відділами.

Три свідомі обмеження:

1. **Без Jira і без обліку часу.** Тут немає замовника, якому треба виставляти години. Одиниця звіту — **крок**, а не година: «додано правило живої сторінки; питання CEO стало відповідати правильно». Це і чесніше (час на роздуми й прогулянки в години не вкладається), і корисніше для читача.
2. **Звіт — не changelog.** `CHANGELOG.md` — хронологія з мітками часу, джерело істини. Звіт — денний зріз: **що зроблено · які рішення й чому · які цифри · що далі**. Звіт цитує changelog, не дублює його.
3. **Українською, у корені проєкту, поза репозиторієм коду.** `docs/reports/` не потрапляє у feature-гілки й не засмічує історію коду (те саме правило гігієни, що й у робочих проєктах).

---

## Шаблон `docs/reports/YYYY-MM-DD.md`

```markdown
# Звіт за DD.MM.YYYY

**Стан:** одне речення — де проєкт зараз.
**Витрачено за день:** $X.XX (індекс $A · eval $B · запити $C)

## Зроблено
- Крок — результат. Посилання на коміт `abc1234` або файл.
  (3–7 пунктів, кожен один рядок, дієслово першим)

## Рішення дня
| Рішення | Альтернатива | Чому так |
|---|---|---|
| … | … | одне речення, без «краще/зручніше» — з причиною |

## Цифри
| Метрика | Було | Стало |
|---|---|---|
| Документів у корпусі | | |
| Strict accuracy | | |
| Hallucinated | | |
| Вартість запиту | | |

## Що не вийшло / свідомо відкинуто
- Чесно, з причиною. Порожній розділ — привід засумніватись у звіті.

## Що далі
- 2–4 пункти, у порядку пріоритету.
```

Обовʼязкові поля — `Зроблено`, `Цифри`, `Що далі`. Решта може бути порожньою, але заголовок лишається: **порожній розділ «що не вийшло» видно, а відсутній — ні.** Це та сама ідея, що й «відсутня записка = явний рядок у зведенні» з документа 04.

## Правило: звіт пише агент наприкінці сесії

```
кінець робочої сесії
        │
        ├── git log --since="<початок сесії>" --format="%h %ad %s" --date=format:%H:%M
        ├── npm run eval        → eval/results/*.json (strict, hallucinated, abstained)
        ├── npm run cost        → $ за день із таблиці llm_calls
        ├── git diff --stat     → які частини системи зачеплено
        └── CHANGELOG.md        → рядки за сьогодні (рішення, зафіксовані по ходу)
        │
        ▼
   агент складає чернетку за шаблоном → docs/reports/YYYY-MM-DD.md
        │
        ▼
   людина: 3–5 хвилин правок і підпис (розділ «Рішення дня» майже завжди правиться —
   агент бачить, ЩО змінилось, але не завжди, ЧОМУ обрано саме це)
```

Три правила, без яких це перетворюється на генератор шуму:

- **Кожна цифра у звіті — з інструменту, не з тексту сесії.** Accuracy береться з JSON eval, вартість — з `llm_calls`, коміти — з git. Число, якого немає в жодному з трьох джерел, у звіт не потрапляє (той самий gate, що в документах 02 і 04).
- **Немає комітів і немає прогону eval → звіту немає.** День роздумів чесно позначається одним рядком «читання, рішень не зафіксовано», а не переказом чернеток.
- **Звіт не переписує вчорашній.** Виправлення вчорашнього факту — рядок у сьогоднішньому: «уточнення до 11.09: …».

Технічно це той самий механізм, який кандидат уже використовує для себе (`~/.claude/skills/daily-wrap`): реконструкція дня з транскриптів агентів, git і логів, а не з памʼяті. Різниця в джерелах — тут замість Jira і VoiceInk стоять `eval/results` і `llm_calls`.

## Як це масштабується на відділи

Звіт цього проєкту й службова записка з документа 04 — **одна конструкція в двох масштабах**:

| | Цей проєкт | Відділ (документ 04) |
|---|---|---|
| Джерела | git log, eval/results, llm_calls, CHANGELOG | Jira, Slack, Drive, таблиці, записи зустрічей |
| Одиниця | крок | задача / блокер |
| Хто пише | агент сесії | агент відділу |
| Хто підписує | розробник | керівник відділу |
| Формат | Markdown за шаблоном | YAML за схемою (валідується) |
| Куди зводиться | `REPORT.md` для рецензента | тижневий звіт для Іванни |
| Правило про цифри | тільки з git/eval/cost | тільки з `numbers[].source` |
| Правило про мовчання | немає комітів → так і сказано | немає записки → явний рядок «немає даних» |

Різниця по суті одна: **у відділі формат машиночитаний (YAML під схемою), тут — людиночитаний (Markdown)**. Причина в кількості: один звіт на день читає людина; двадцять записок на день зводить код, і йому потрібна схема. Перехід між ними — це додати фронтматер до шаблона, а не переписувати процес.

Що переноситься без змін: агент реконструює з машинних слідів → людина підписує → відсутність даних видима → числа тільки з інструментів → блокери мають адресата.

## Що показати на демо

1. **`docs/reports/2026-09-11.md`** поруч із `CHANGELOG.md`: видно, що це різні жанри — хронологія проти денного зрізу з рішеннями й цифрами.
2. **Згенерувати звіт наживо** наприкінці демо-сесії: `git log` + `npm run eval` + `npm run cost` → чернетка за 20 секунд → одна правка людини в розділі «Рішення дня».
3. **Показати порожній розділ** «що не вийшло» в одному зі звітів і пояснити, чому заголовок лишається.
4. **Поставити поруч** шаблон звіту й YAML-схему службової записки з документа 04 — одна конструкція, два масштаби.
