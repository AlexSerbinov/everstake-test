# Manual and automatic corpus updates

Open **Updates** in the application menu. Enter the server's `ADMIN_TOKEN`, adjust the global automatic switch, maximum new videos per run and individual source schedules, then select **Save settings**. The schedule accordion contains source enablement, intervals in hours and priority. Use **Update selected source**, **Check due sources** or **Update all enabled sources** to enqueue work. Run buttons use saved settings. Automatic execution defaults to off; enabling it is an explicit operator action. The worker starts with `npm start` and only runs while the application is running. This change has been verified locally; the hosted service must receive the new code before its menu changes.

One source executes at a time. Requests for a queued/running source reuse its job; a manual request promotes a paused scheduled job. Priorities determine queue order, never evidence authority. A failed source waits its configured interval before another automatic attempt; manual retry bypasses that delay. Disabling automatic updates pauses queued scheduled work, but does not interrupt an already running source. A process restart retains settings and queued jobs. Abandoned running jobs become interrupted once the three-minute worker lease expires; select that source again to retry. The UI shows job phases, success/failure and recorded counts/costs. No evaluation is run automatically.

## Preservation and activation

Web refresh uses the existing robots-aware bounded crawler, source allowlists, extraction, sanitation, deduplication and chunk embedding cache. It starts from a SQLite backup and only activates validated text, vectors and corpus version in one transaction. Partial collection, pending crawl pages or provider failures retain the serving corpus. Old document revisions, historical answers, billing rows and unrelated inactive documents imported concurrently are retained; a changed serving baseline rejects stale activation. A missing or failed URL is never a deletion instruction. Same-content checks can update observation metadata; they do not invent new publication dates. Unchanged chunks reuse embeddings, although web pages are fetched again rather than promising conditional HTTP requests that are not implemented.

The application waits for its current question before running queued work and refuses new questions while that source updates, so an answer cannot mix the application's pre/post-update corpus. CLI maintenance or independent writers should not be run concurrently with questions; this is a single-serving-process design, not distributed snapshot isolation. Staging files remain for inspection and need a retention policy. Retry collection failures by source; `refresh-resume` is intended for a completed collection whose embedding/activation stage failed, not an incomplete crawl.

## Incremental YouTube

Metadata-only discovery checks the official channel in `config/youtube.yaml` and the bounded searches in `config/update-discovery.yaml`. yt-dlp supports flat playlist extraction and bounded search without downloading each video's media ([official options](https://github.com/yt-dlp/yt-dlp#usage-and-options)). Search metadata is a candidate hint, never answer evidence. This is bounded discovery, not a claim to find every video online; absent videos are not deleted. Existing inventory IDs, stored transcript jobs and corpus video IDs are skipped before detailed metadata/audio/STT. Historical unprocessed inventory candidates are deliberately not turned into a new mass paid batch.

Only newly discovered IDs enter the durable update registry. Full metadata is fetched for a bounded number, then the existing screening policy decides accepted/excluded/needs-review. Unknown duration cannot trigger paid processing. Accepted videos use Soniox and the existing Gemini speaker review; only eligible testimony becomes a document. The original transcripts, jobs, review results and pending video state survive failed activation. A completed STT job is read directly without redownloading audio or creating another job. Ambiguous provider submission is reconciled by the existing Soniox adapter; it is never blindly resubmitted. Media or policy revision reprocessing remains an explicit maintenance operation, not a hidden refresh side effect.

New artifacts live in ignored `data/updates/`, with registry/review/document state in the serving SQLite settings and existing `youtube_jobs`. Initial reviewed exports and inventory files are read without rewriting them. Keep the serving DB and data directory persistent across deploys. New Gemini/embedding calls use the configured provider budgets; Soniox reservations use the configured YouTube run limit and session policy. Measured usage, reserved forecasts and unknown Soniox billing remain distinct. A successful bounded video run can still report pending or needs-review candidates; those counts describe backlog, not complete YouTube coverage.

## API and checks

- `GET /api/updates`: settings, source due times, latest 100 jobs and corpus version; no paid work.
- `PUT /api/updates/settings`: complete validated settings, with `Authorization: Bearer <ADMIN_TOKEN>`.
- `POST /api/updates/run`: `{ "sourceId": "youtube" }`, `{ "due": true }` or `{}`; returns queued/deduplicated jobs with HTTP 202.

Missing/wrong credentials cannot start work or edit schedules. Unknown/disabled sources and invalid intervals are rejected. The original CLI refresh commands remain available for web sources; `refresh-due` uses saved per-source schedules. The browser displays the latest 30 jobs and cleans up polling on navigation. Tests use isolated databases and fake providers; the local browser smoke covers saved settings, successful/failed manual jobs, token clearing and mobile layout without API spending. Fresh YouTube discovery and paid processing were not run against the serving corpus for this change.
