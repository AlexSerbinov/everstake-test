## Корисне: зберігаємо у простій формі

| Метод зі старої роботи | Чому корисний | Простий крок нової реалізації |
|---|---|---|
| Конфіг джерел і запуск одного source ID, Claude | Новий документ не вимагає зміни crawler code | Додати source entry, preview, crawl лише його |
| Robots, паузи, bounded requests, обидві версії | Корпус зібраний контрольовано | Один fetch adapter з явними status/reason |
| Причина кожного exclusion й походження URL | Можна пояснити, чому факт не знайдено | Corpus card: звідки URL, що сталося, що ще pending |
| Власна editorial date, окремо sitemap/HTTP | Міграція сайту не робить старі факти новими | Зберігати дату й тип доказу дати, не один універсальний timestamp |
| Exact і near-duplicate grouping | Копії не стають більшістю | URL/content candidates + перевірка схожості та матеріальних відмінностей |
| Змістовні chunks і read із продовженням | Примітка не губиться за snippet limit | Розділи, таблиці, offsets і сусідній контекст |
| Hybrid search та rank fusion, Claude | Шкали BM25 і cosine не потрібно штучно прирівнювати | Об'єднати два списки за позиціями; коефіцієнти фіксувати й перевіряти |
| Фільтри до top-k, різноманітність документів/часу | Одна сторінка не займає всі місця | Фільтрувати до обрізання, історичні slots лише для часових питань |
| Реєстр evidence IDs, обидві версії | Посилання стабільні протягом запиту | Зареєструвати точний видимий уривок один раз |
| Один sanitizer для search і read, escaped framing | Повне читання не обходить захист індексу | Єдиний evidence-сервіс, включно з body та metadata serialization |
| Видалення вставленої AI-інструкції зі збереженням факту | Захист не має знищувати відповідь разом з атакою | Тест: корисна фраза залишається, команда вилучена |
| Structured finish і обмежений loop | Контроль відповіді й вартості у коді | Тільки search/read/calculate/submit, кроковий і часовий бюджети |
| Зупинка без нових доказів, Claude | Не витрачаємо гроші на однаковий пошук | Рахувати нові уривки, а не лише нові document IDs; врахувати непрочитане продовження |
| Нормалізація сум/одиниць і калькулятор | 1.6M і 1,600,000 можуть означати те саме | Перевіряти кількість, одиницю, валюту, знак і контекст операндів |
| Показ found/dropped/shown/cited та причин, обидві версії | Видно місце збою | Серверний trace з однієї структури для UI й evaluation |
| Cost ledger + stage runs + receipt, насамперед Claude | Враховані всі експерименти, повтори й judge | Один measurements-сервіс, сума за call IDs |
| Evidence judge на збереженій відповіді, Codex | Оцінюємо саме доставлений результат | Не переопитувати асистента під час grading |
| Той самий runner в API й eval, виправлення Codex | Тести вимірюють систему на демо | Один `answerQuestion` і перевірка цього контракту |
| Trust Score з поясненням, обидві версії | Людина бачить якість доказової основи | Окремий чистий scorer, flags невизначеності, перевірка упевнених помилок |
| Conditional GET + content hash + cache embeddings | Оновлення не повторює весь оплачений build | Один refresh workflow, нові та змінені chunks |
| Adversarial documents через реальний ingest | Перевіряється весь шлях, а не добра воля моделі | Clean/injected pairs в ізольованій тестовій базі |
| Розділення code/model/human у PROCESS | Автоматизація має зрозумілу межу відповідальності | Code збирає й рахує, модель готує текст, людина ухвалює бізнес-висновок |

Rank fusion пропонується як початковий алгоритм пошуку, а не гарантія кращої точності. Near-duplicate метод також вибирається за виміряними помилками: для кількох сотень документів допустима проста pairwise-перевірка зі звітом про квадратичне масштабування; LSH додається лише за потреби й окремо перевіряється на containment.

## Що спрощуємо або не переносимо

| Рішення | Проблема для нового завдання | Заміна |
|---|---|---|
| `CEO → /ai-info,/about` у Codex | Питання визначає дозволений URL через спеціальну гілку | Пошук ролі/організації/часу + призначення джерела |
| Закриті 21 fact keys у Claude | Ledger приймає CEO/CCDO, але не довільну роль; інші факти можуть лишитися лише у звичайному пошуку | Query-time claims із цитатами, без глобального словника посад |
| Тотальна extraction фактів дешевого LLM | Другий індекс, повторний billing, синхронізація та нормалізація | Спочатку evidence-only відповіді; окремий fact store лише після виміряної потреби |
| Штраф документа за `key + year + different number` | Різні компанії, продукти, підмножини й lower bounds можуть бути сумісні | Порівняння лише зіставних тверджень поточного питання; сумнів позначаємо |
| Окремий gate для institutional fee чи конкретного заперечення | Закриває приклад, але не клас помилок | Загальні scope/condition правила й тести на різних предметах |
| Автоматичний вибір earliest copy як істини | Походження передруку й актуальність версії — різні питання | Окремо duplicate lineage та revision history; не губити виправлення |
| Масовий rewrite старого домену чи видалення `.md` | Схожі URL не завжди одна сторінка | Підтверджені redirects/canonical + content; mapping тільки з доказом |
| Незмінний sitemap lastmod як остаточний доказ | Sitemap може бути неповним або застарілим | Hint плюс перевірки HTTP/content за простою політикою |
| Голос відразу стає first-party через згадане ім'я | Згадка не дорівнює цитаті, цитата не доводить автентичність | Publisher і attributed speaker окремо, unknown дозволено; без people-sync платформи |
| «Стороння думка не може встановити факт» як універсальне правило | Незалежний аудитор може мати кращий доказ у своїй сфері | Компетентність і предмет доказу, а не безумовна перевага компанії |
| Самооцінка моделі у Trust | Не є незалежною перевіркою | Не включати її в загальний score |
| Подвійний runtime single-shot/agent із різними gates | Eval або API легко використовують інший шлях | Одна production функція; baseline окремий явний runner зі спільними gates |
| Exact-match фрази відмови | Переклад/перефразування ламає тести | Typed status і reason code, окремо human text |
| Багато switch для нового інструмента | Легко забути schema, handler або UI label | Один tool registry, спільний executor |
| Мікросервіси для кожного блоку | Більше deployment і network failure замість читабельності | Окремі сервісні папки в одному TypeScript-застосунку |
| Ed25519, freshness UI-конструктор, широкий live toolbox | Зайва складність для обраного corpus-only scope | Evidence snapshot/receipt, проста команда refresh, MCP лише як baseline |

Закритий ledger Claude не означає, що вся стара система гарантовано не відповість про CMO: вона також має текстовий пошук. Проблема — нерівномірність маршрутів і потреба підтримувати список фактів. У новій версії роль не повинна визначати іншу архітектуру відповіді.

## Формулювання аудіосценаріїв, які потрібно уточнити

1. **«Найгірше від injection — тільки відмова».** Це не доведено: неправильна нечислова заява або число про інший предмет можуть пройти структурні gates. Зберігаємо багатошаровий захист і вимірюємо як пропущені атаки, так і хибні відмови.
2. **«Сторінка сьогодні правдива станом на сьогодні».** Fetch доводить спостереження тексту, не чинність кожного твердження.
3. **«Гейт нічого не знайшов — весь запит коштував нуль».** Нової генерації може не бути, але попередні model turns і query embeddings уже коштували грошей.
4. **«API error не входить у знаменник accuracy».** Основна end-to-end accuracy рахує всі задані питання; додаткову accuracy без інфраструктурних збоїв можна показати окремо з явним знаменником.
5. **«Два домени — два незалежні підтвердження».** Піддомени можуть мати одного видавця; різні медіа можуть цитувати ту саму заяву. Незалежність доказу не виводиться лише з host.
6. **«Кожне число є в доказах — отже, вигадки немає».** Число може стосуватися іншої компанії або бути перенесене з прикладу в гарантію. Invented/unsupported claims перевіряються за змістом.
7. **«Всі старі зелені тести доводять нову поведінку».** Частина тестів документує старі вади. Під час перенесення перевіряємо потрібний контракт і окремо зберігаємо історичну знахідку.
8. **Історичні суми та розміри корпусу.** Не переписувати в план як актуальні гарантії; звіти нової версії генерувати з її зафіксованого run manifest.

## Перевірка загальності

Після зміни правила запускати сімейство тестів, а не один приклад: CEO/CMO/нова роль; інші назви організацій; інші URL; інші числа й валюти; переставлені джерела; дублікати; невідомі дати; явне виправлення; різні продукти з однаковим показником. Один і той самий pipeline має дати правильну відповідь або чесну відмову без правок коду.

Шаблонні тести не замінюють незалежні питання: до фінальної перевірки додати природно сформульовані запити, яких не було при налаштуванні. Жодна нова рекомендація в цьому документі не вважається перевіреною якістю до реального запуску.

## Що варто показати на захисті

Доповнення за двома скриншотами й переглядом локального frontend 2026-09-13: до базового демо входять live timer і зв'язок цитат із правою панеллю джерел із Claude, а також поступовий показ знайдених уривків, repeats і dropped reasons із Codex. Реалізаційний план — [LIVE_EXPERIENCE.md](LIVE_EXPERIENCE.md). Бюджетний provider error та RuntimeError зі скриншотів використані як вимоги до error states, а не як нові evaluation-запуски.

Вісім простих сцен: як джерело потрапило в корпус; чому копію не порахували вдруге; що sanitizer прибрав і що залишив; як read знайшов уточнення; чому код відхилив чернетку; з чого складається Trust; скільки коштував весь запит; як та сама логіка відповіла на нову роль після додавання джерела.

Знахідки про втрачений графік і межі маркетингових тверджень лишаються корисними прикладами якості даних. У базовій версії достатньо coverage warning та показу межі доказів. Масовий OCR, юридичний експерт чи процес погодження всіх корпоративних заяв сюди не входять.
