- Claude `src/crawl/extract.ts` і [технічні нотатки](../everstake-defence-audio/_notes/01-claude-corpus-index.md) пояснюють, чому sitemap lastmod після міграції омолоджував старі статті. Пізніше [READINESS](../projects/personal/everstake-test/docs/evaluation/hard-v1/READINESS.md) описує виправлення 369 дат — інший етап, не взаємозамінні числа.
- У нотатках є **дев’ять копій пресрелізу**, а окремо — **дев’ять нерелевантних музичних відео** з однойменного каналу. Це різні проблеми: синдикація не є неправдою, а збіг назви каналу не доводить його зв’язок із компанією.
- Claude `src/refresh/refresh.ts` підтримує вибір типів джерел і force-перевірку; `schedule.ts` перевіряє due work. Codex `app/refresh.py` також має due intervals і force. Беремо можливість планового/позачергового запуску; не переносимо складний конструктор тарифів та частот.

## Два шляхи адаптації

**Нові дані підтриманого формату.** Доданий URL у дозволеному джерелі, нова сторінка, змінені цифри чи нова посада проходять звичайний ingestion/index і стають доступними пошуку без зміни prompt, коду чи деплою. Модель читає нові докази тим самим набором tools. Новий домен потребує source config із походженням, призначенням, дозволеними адресами й лімітами; текст сайту не може сам підвищити власний авторитет.

**Новий формат або нова вимога.** Якщо extraction губить таблицю/схему, документ позначається unsupported/needs_review, а не нібито успішно проіндексованим. Автор за допомогою Codex змінює конкретний adapter/правило, додає малий fixture, перевіряє, збирає застосунок і передеплоює в межах окремо дозволеної реалізації. Потім повторює лише зачеплений ingestion; нова parser/policy version робить старий кеш непридатним там, де змінився результат. Система не переписує свій код чи критерії істини самостійно.

Публічні файли, надані на захисті, можна прийняти через простий CLI import для підтриманих форматів із source metadata; вони проходять той самий шлях, що crawler. Архіви/нові формати — тільки після підтримки адаптера. Завдання обмежене публічними даними. Складний uploader не потрібний для першого демо.

## Плановий та позачерговий збір

Майбутній контракт CLI (поки не реалізовані команди):

```sh
npm run corpus -- refresh --due
npm run corpus -- refresh --source company-docs --now
npm run corpus -- discover --source company-docs
npm run corpus -- refresh --all --now
npm run corpus -- import --file public-notes.md --source supplied-public-docs
```

`--due` бере джерела за строком наступної перевірки; `--now` обходить лише розклад. Robots, allowlist, budgets, sanitation й перевірки залишаються. `--all --now` означає перевірку всіх джерел, а не безумовну повторну генерацію всіх embeddings. Discovery знаходить нові URL, refresh перевіряє вже відомі; можна об’єднати їх одним workflow для обраного джерела. Перебудова extraction/index після зміни алгоритму — окрема дія, не прихований побічний ефект refresh.

Конфіг джерела: `refreshInterval`, `priority`, `enabled` плюс чинні limits. Пріоритет означає порядок перевірки, **не авторитет і не множник Trust**. Позачергове оновлення обраного джерела йде наступним після поточної безпечної одиниці роботи; дедуп черги не допускає двох однакових активних робіт. Один worker і persistent job table достатні, без Kafka чи окремого сервісу черг. Restarts показують interrupted і дозволяють resume; незавершену публікацію не видавати за готову.

У блоці Corpus додати: «Перевірити заплановані», «Оновити це джерело зараз», «Знайти нові сторінки»; повне оновлення — додаткова дія з явним scope. Видно чергу, обране джерело, етап, counts і поточну ціну/unknown usage. Для публічного демо mutations доступні лише оператору через простий server-side admin token/сесію або CLI; звичайний відвідувач не може витрачати crawl/API бюджет. Токен не вбудовується у публічний frontend. На локальному демо достатньо CLI для керування й read-only UI прогресу.

## Що відбувається після додавання документа

1. Створити run/job; зафіксувати джерело, причину запуску й бюджет. Discovery/fetch/import дають raw snapshot із provenance.
2. Extraction → дати з походженням → sanitation → duplicate/version grouping → chunks. Та сама обробка для corpus-v1, refresh та імпорту; ручний разовий cleanup не є основним механізмом.
3. Витягнути й embedding-обробити лише потрібні нові/змінені chunks. Показати added/changed/unchanged/duplicates/excluded/failed/pending, а не лише число успіхів.
4. Перевірити staging snapshot і короткі deterministic invariants; атомарно активувати новий corpus version. Поточна відповідь завершується на версії, з якої почалася; наступне питання бере нову. Trace, citation offsets, receipt і Trust прив’язані до тієї самої версії.
5. Якщо scope run не завершився або перевірки впали — лишити активну попередню версію, показати partial/failed і відновити обробку. Не заявляти повне успішне оновлення. Старі snapshot та відповіді залишаються доступними з датою.
6. Перевірити зачеплене питання до/після. Evaluation автоматично не запускати: воно коштує грошей. Позначити старий eval як такий, що оцінював попередній corpus. На новій версії перевірити негативні еталони й лише потім запускати потрібний тест або фінальний набір.

Якщо є answer cache, його ключ включає corpus/config/model version. Старий кеш не видається за відповідь на нових даних. Найпростіший початковий варіант — не мати answer cache, зберігати лише історію запусків.

## Перенесена стаття не стає новою

Зберігати окремо `publishedAt`, `updatedAt`, `fetchedAt`, `effectiveAt` (якщо явно встановлено), date precision і date provenance. `Last-Modified`, sitemap lastmod та GitHub commit time — технічні сигнали змін; не автоматичні дати публікації/чинності факту. Не переносити старий fallback HTTP Last-Modified → publishedAt як загальне правило.

Приклад користувача «стаття квітня 2025 переїхала пізніше» — контрольний synthetic-case, не нове підтверджене історичне вимірювання. Через redirects/canonical hints і порівняння змісту пов’язати стару й нову адреси; зберегти початкову підтверджену дату та обидва URL. Не переписувати домени за списком брендів. Canonical hint сам по собі не дозволяє злити різні тексти. Якщо достовірної старої дати немає — unknown; якщо сигнали суперечать — date conflict, а не вигадане «точне» число.

Переїзд без зміни змісту створює alias/спостереження. Суттєва редакція — нова document version із попереднім snapshot, не стерта копія. Первісна дата статті не повинна приховувати реальне пізніше оновлення конкретного факту; потрібний уривок або content diff і явні часові межі. Простий текстовий diff — діагностика, не доказ дати набуття чинності.

На source card: «Опубліковано», «Оновлено» за наявності, «Перевірено»; додатково коротка історія «старий URL → перенесено/вперше спостережено тут → зміст змінено». Відсутню точну дату переїзду не домислювати. У synthesis — хронологія фактів із цитатами; це відрізняється від історії завантажень. Окремий великий timeline dashboard не потрібний.

## Очищення під час роботи системи

**На кожному ingestion/index:** структурно відділяти метадані відосновного тексту, прибирати інструкції для AI, знаходити копії та ймовірну синдикацію, перевіряти походження джерел, зберігати raw і причини. Неправильно записане число позначати, не «виправляти» домислом. Непевні near-duplicates не видаляти безповоротно. Зміна extraction/sanitation policy потребує контрольованого reprocess; не змішувати старі й нові уривки в активному snapshot.

**Під час кожної відповіді:** collapse відомих copy groups; перевірити видимі кандидати на повторення й походження, яке міг пропустити індекс; не рахувати перепублікації незалежними голосами. Unknown independence позначати консервативно. Дочитувати релевантні уточнення; порівнювати subject/metric/unit/time/scope, розділяти історичну зміну й реальний конфлікт, атрибутувати сторонні твердження. Це не універсальний детектор неправди і не глобальне видалення документа після модельної незгоди.

Нові копії старого пресрелізу не перемагають свіже пряме підтвердження. Але старий пресреліз залишається доказом історичного оголошення. Дев’ять однойменних нерелевантних відео відхиляє перевірка походження/тематики, не правило «видалити дев’ять документів». Існуюча межа sanitation при індексації зберігається: переносити весь захист лише в prompt при відповіді не можна.

## Репетиція нових даних

Без платного повного eval перевірити fixtures: новий релевантний документ; дев’ять копій; змінений факт; переїзд без зміни; різні дати; новий непідтриманий формат; інструкція для AI; timeout; натискання refresh двічі; запит під час activation; restart. Для live-прикладу: показати стару відповідь → додати публічний документ → targeted refresh → progress/diff/cost → нове питання з новим corpus ID й датованим джерелом. При конфлікті демонструвати чесне пояснення, не вимагати зміни відповіді за будь-яку ціну.

Місця в коді: `workflows/refresh-corpus.ts` керує процесом; `crawler/check-source-changes.ts` та `discover.ts` — збором; `indexer/deduplicate.ts` — групами; `storage` — snapshots/jobs/activation; `evidence/verify-answer.ts` і `answer/answer-question.ts` — фінальними доказами. Нові маленькі файли: `crawler/resolve-source-dates.ts`, `storage/activate-corpus.ts`, `web/features/corpus/refresh-controls.ts`, `source-history.ts` біля `answer-sources`. Їх створюють лише разом із відповідною поведінкою, не як порожній каркас.
