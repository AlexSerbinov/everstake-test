## 1. Єдине джерело цифр із першого виклику

### Підготовка через агентів і подальший API-шлях

Початковий корпус планується готувати за допомогою coding agents у межах наявної підписки. Розрізняємо три категорії:

- `subscription_assisted_preparation`: дослідження, створення crawler та QA агентами. Записати метод, дату, артефакти, доступні дані використання й межі покриття. Якщо точні токени або вартість цієї сесії недоступні — `unknown`/`not separately metered`, не вигадана сума за API-тарифом.
- `initial_index_api`: фактичні embedding та інші API-виклики початкового build. Вони платні за виміряним usage навіть якщо підготовці текстів допомагав агент із підписки.
- `refresh_api`: фактичні API-виклики наступних оновлень, включно з retries, embeddings і потрібною модельною extraction. HTTP-перевірки та звичайний parser мають окремі ресурсні виміри.

Відсутність окремого API-рахунку за роботу агента не означає $0 повної вартості підготовки. Фіксовану підписку показувати окремо за фактичним платежем, якщо він наданий; частку, віднесену до проєкту, лише за явно погодженим методом. Наявний API ledger залишається точним total усіх записаних API-викликів; поруч показувати preparation/subscription coverage. Це не замінює вимогу виміряти вартість індексації за §5.6.

Для corpus-v1 та кожного refresh зберігати спосіб обробки (`code`, `subscription_agent`, `api`), версії parser/prompt, посилання на оригінал і прийняті правки. Порівнювати якість agent-assisted та автоматичного шляху на тих самих документах; не оголошувати їх еквівалентними лише за збігом схеми JSON.

### Схема обліку

SQLite-таблиці:

- `runs`: run_id, parent_run_id, experiment_id, stage, question_id, timestamps, status, machine, wall_ms, cpu_ms, sampled_peak_rss, items, bytes, config/code/corpus hashes.
- `api_calls`: call_id, run_id, attempt, provider request ID якщо доступний, provider, model, raw usage, uncached/cached input, output/thinking/cache-write за схемою провайдера, price snapshot, cost, status, error, latency.

Реєструвати виклик до запиту і завершувати запис після відповіді. Після crash незавершені виклики залишаються видимими. Відповідь із billing usage враховується навіть якщо наступна валідація чи парсинг JSON впали. Retry — окрема спроба, не заміна попереднього запису.

Provider adapter нормалізує токени без подвійного підрахунку cached input або thinking. Формула для провайдера перевіряється на його офіційній схемі usage і тарифі. Оригінальне usage зберігається для аудиту. Невідомий model price або втрачений usage — `unknown`, не нуль. Показувати відому суму й кількість неповних записів.

Усі API-клієнти проходять через один wrapper у TypeScript model-client, облік належить `services/measurements`. Одночасні запити ізолюються через context-local run ID (Node.js AsyncLocalStorage). Загальний total рахується за унікальними API-call rows; parent/child stage totals не додаються вдруге.

## 2. Чотири різні суми

1. **Витрачено загалом:** усі записані API-спроби нової реалізації, включно з development, невдалими відповідями, повторними індексаціями, baseline, evaluation і judge.
2. **Один build:** один успішний повний pipeline_run зі своїм corpus snapshot; не сума найдешевших чи найбільших етапів різних запусків. Cached incremental build показувати окремо від cold build.
3. **Один запит:** усі його model turns, embeddings та платні tool calls; окремо статус, повна ціна й час. Середнє лише для позначеного набору/моделі/версії, поруч кількість зразків і медіана.
4. **Evaluation:** запити до системи та grading окремими subtotal; повна вартість прогону включає обидва без подвійного рахунку.

Безкоштовний код означає $0 API-витрат, а не відсутність витрат інфраструктури. Облік CPU, RSS, часу, документів і bytes зберігається. RSS є sampled/process-wide; для паралельного сервера не видавати його за точну пам'ять одного запиту. Ресурсні benchmark запускати послідовно на одній машині.

UI, receipt і COST.md обчислюють суми тим самим SQL/агрегатором. Тарифи фіксуються на момент виклику; зміна таблиці цін не переписує історію. За доступності provider billing export виконати звірку, окремо показати credits, націнки, податки та розбіжності.

Для живого UI окремо вимірювати client elapsed/time-to-first-event і server wall/step durations. Клієнтський таймер не підміняє server accounting; pending provider usage не показувати як підтверджені нульові витрати. API totals зберігаються також на error/cancelled runs. Stream interruption не запускає автоматично новий платний запит.

## 3. Baseline: три різні питання

| Порівняння | Що воно доводить | Контроль умов |
|---|---|---|
| Нова версія проти поточного Codex | Чи спрощення зберегло якість | Ті самі документи, питання, модель, settings, corpus-only режим; фіксувати різницю chunking/index |
| Агент проти простого RAG | Чи окупаються додаткові search/read кроки | Той самий індекс, модель, базові правила й фінальні gates; RAG робить один пошук і одну генерацію |
| Нова версія проти Everstake MCP | Де власний корпус корисніший за офіційний baseline | Задокументувати MCP version/tool/timestamp; порівняти спільні типи питань, не приховувати відмінність джерел |

MCP-порівняння обов'язкове за §5.7. На етапі виконання перевірити його фактичні можливості. Для static company text зберегти точний MCP output і дати тій самій моделі питання з цим контекстом. Live operational tools оцінити окремо: не вимагати від frozen corpus сьогоднішньої ставки. Розрізняти MCP transport cost і вартість LLM, який формує відповідь. Не будувати ще один складний агент для baseline.

Історичні метрики Claude — референс обліку, не контрольований benchmark нової версії: інші корпус і запуски.

## 4. Evaluation

- Відібрати один основний набір із 20 питань: 5 базового походження та 15 складних, включно з 5 негативними. Еталони перевірити на зафіксованому корпусі.
- До запуску зафіксувати обов'язкові факти, неприйнятні висновки, допустимі межі часткової відповіді та evidence spans. Зміна еталона має revision і пояснення; старі відповіді не стираються.
- Агент не бачить еталонів, source IDs чи категорії тесту. Corpus не містить eval-файлів, defence notes і готових відповідей.
- Показувати question/reference/system answer/verdict. `correct`, `partial`, `wrong`, `abstained`, `error` розрізняти; `invented` — незалежна ознака матеріального непідтвердженого твердження.
- Основна accuracy = повністю правильні / усі питання, включно з помилками. Окремо правильні негативні відмови, зайві відмови, часткові відповіді, вигадки та provider errors.
- Окремо перевірити retrieval coverage: потрібний доказ присутній у корпусі, пережив extraction, потрапив у контекст. Посилання з правильними словами ще не підтверджує висновок.
- Arithmetic перевіряти за операндами/формулою/одиницями; результат може не бути дослівно в джерелі.
- Детерміновані перевірки доповнюються model judge і ручним переглядом фінальних 20 відповідей. Технічний gate failure не може стати PASS лише за рішенням judge.
- Зберігати сирі відповіді кожного запуску; не вибирати найкращу з retries. Для нестабільних випадків зробити повтори обох систем і показати всі результати.
- Основний evaluator викликає той самий TypeScript `answerQuestion`, що API й CLI. Unit-тести старої вади не переносити як вимогу до нової системи; gates перевіряти незалежними очікуваннями, а не викликом тієї самої функції як oracle.
- Нові фінальні питання до запуску не використовувати для налаштування. Після використання вони стають регресійними.

Захисні тести: clean/injected pairs, незнайомі назви компаній, однакові цифри про різні об'єкти, старі/нові версії, множення дублікатів, невідомі дати, втрачений контекст, provider outage. Ціль — нуль виявлених вигадок і відсутність регресій захисних меж; статистичної гарантії це не дає.

### Trust Score у вимірюваннях

Trust Score входить у нову реалізацію. Для кожної підтриманої відповіді зберігати бал, складові, ваги, причини й версію policy; додати колонку до EVAL.md. Для відмов та errors — порожній бал із поясненням. Витрати й час code-only scoring включати в receipt ($0 додаткових model calls).

Correctness оцінюється незалежно: judge і людина не бачать Trust Score під час виставлення verdict. Бал не бере правильну відповідь або оцінку evaluator як вхід.

У звіті показати кількість зразків і частку повністю правильних відповідей за діапазонами score, середні бали правильних і помилкових відповідей, усі випадки високого бала з вигаданим чи неправильним твердженням. За наявності обох класів обчислити кореляцію бала з correctness; без варіації — `n/a`. Часткові відповіді аналізувати окремо, щоб бал доказів не приховував неповноту. Малі авторські набори не доводять калібрування ймовірності.

Тести: повторний розрахунок на тих самих входах дає той самий бал; дублювання джерела не підвищує score; незалежність не визначається лише різними URL; явний зіставний конфлікт знижує відповідну складову; дата завантаження не підмінює дату факту; релевантна історична дата не штрафується як застаріла; невідома metadata не дає максимум; сильне стороннє джерело з іншої теми не підвищує бал непідтвердженого твердження; gates не можна обійти високим score.

Ваги підбирати лише на development-наборі, потім зафіксувати й перевірити на нових питаннях. Для baseline без аналогічного score ставити `n/a`, а не вигадувати еквівалент; основне порівняння систем залишається за correctness, вигадками, ціною та часом.

## 5. ×50

Індекс: фактичні embedding/extraction tokens × зафіксовані тарифи; ×50 лише з явним припущенням про подібні розміри документів і обсяг обробки.

Запит: не множити на 50 за збільшення корпусу. Фіксований context budget обмежує prompt size, але кількість search turns і retrieval latency можуть змінитися. Відокремити припущення від фактичного заміру більшого корпусу.

CPU/time дедуплікації не оголошувати лінійними без аналізу алгоритму. Зокрема, all-pairs порівняння росте квадратично. Збільшення workload питань у 50 разів — окремий сценарій від corpus ×50.

## 6. Перевірки обліку перед готовністю

- Сума унікальних API-call rows = total на UI = total у звіті.
- Повторні й невдалі billable виклики присутні; невідомі charges не приховані.
- Parent evaluation + child question не подвоюють суму.
- Витрати judge й baseline не губляться в загальному spend.
- Cache tokens і thinking не рахуються двічі.
- Перезапуск процесу не скидає історію; паралельні питання не змішують receipt.
- Cold build і incremental refresh мають різні run IDs та результати.


## Перевірка узагальнення після CEO-референсу

У temporal test family фіксувати subject, property/role, scope та часові межі джерел. Порівняти незмінний алгоритм після заміни організації, посади, URL і порядку результатів; додати відсутню роль, однакові за часом суперечливі джерела та flood копіями. Очікування — структура тверджень і допустимі висновки, не дослівна відповідь зі скріншота. Старе оголошення саме по собі не доводить поточну посаду; свіже fetch саме по собі не доводить нову effective date. Помилкове приписування ролі/дати рахується invented fact навіть за валідних refs.

Це відомі регресії. Переносимість додатково перевірити новим питанням, яке не використовували для налаштування правил. Не заявляти повну семантичну гарантію на підставі проходження кількох перейменованих fixtures. Після зміни corpus або policy повторити фінальні baseline/agent runs на однаковому snapshot; не зшивати вибіркові успіхи в нові 20/20.


### Уточнений обсяг evaluation

За новим побажанням користувача виконати один набір із 20 питань (5 базових + 15 складних, із них 5 негативних); порівняти з simple-RAG baseline. Agent і baseline мають окремі звіти на незмінних умовах, а не вибірка найкращих спроб. Runner, рубрика, ungraded/error states і однакові UI/Markdown-метрики перевіряються окремо. Деталі та каталог hard cases — у [EVALUATION_PLAN.md](EVALUATION_PLAN.md). Читання результатів на фронтенді не запускає нових API-викликів.


## Таблиця Costs: кожна відповідь і все витрачене

Погоджена обов’язкова деталізація UI:

| Рівень | Що показувати |
|---|---|
| Кожна відповідь | Question, run ID, дата, status, модель, tokens, час і сума всіх її API attempts; посилання на receipt |
| Кожний запуск збору | Initial/import/discovery/refresh/index, source scope, нові/змінені/unchanged counts, usage і вартість |
| Evaluation | Answer subtotal, judge subtotal, baseline subtotal; кількість питань і завершеність |
| Загалом | Сума унікальних API-call записів усіх запусків, включно з development, помилками й повторами |

Таблиця має фільтри category/date/model/status та рядок subtotal видимої вибірки. Незалежно від фільтрів видно total all-time для нового проєкту; історичні $12.12 старої версії не додаються до нього. Дочірній виклик входить у суму один раз: не додавати parent run total до тих самих child costs. Історія питань не групується так, щоб зникли невдалі attempts. Unknown/pending usage — окрема позначка й count, не $0.00000; показувати «обліковано X, N викликів без повної вартості». Маленькі суми не округляти до нуля; receipt має достатню точність.

Provider usage × зафіксований тариф — облікована API-вартість, окремо від billing reconciliation, підписки, податків і хостингу. Фактичний provider charge зберігати за наявності; спосіб обчислення позначати. Відповідь без додаткового API виклику може мати $0 incremental cost; це не обнуляє попередню індексацію. Платна ціна майбутнього evaluation не обіцяється наперед: 20 agent answers + за потреби 20 baseline answers + judge/retries окремо. Докладна рубрика дозволяє ручний grading без judge API.

Перевірка Costs: fixture із успішним запитом, retry, provider error, refresh та evaluation/judge; total, subtotals, receipt й COST.md узгоджені, жодної подвійної суми. Жодного нового платного виклику під час перегляду таблиці.


## YouTube: окремі видимі етапи

YouTube включений у план. Поруч із Soniox STT обов’язково обліковувати окремий Gemini 3.8 Flash прохід `youtube_speaker_review`: video/window IDs, input/output/cache/reasoning usage за provider fields, status, час, attempts і тарифи. Screening, identity attribution та embeddings теж окремі стадії. Не приховувати витрати повторно переданого контексту довгих відео. Кеш перевірки не обнуляє історичний cost; невдалий review не показується як успішний. Точна виміряна ціна Soniox залежить від доступного usage/billing, а тривалість × приблизний годинний тариф є прогнозом. Деталі та pricing sources — [YOUTUBE_PLAN.md](YOUTUBE_PLAN.md), розділ 11. `costs/YouTube/` міститиме exports єдиного ledger, а не незалежний лічильник.

Уточнення YouTube: первинна identity/role attribution та перевірка labels виконуються одним Gemini-проходом `youtube_speaker_review`; його usage рахується один раз. Додаткові уточнення імені/ролі мають окремі attempts, а не дубль первісного cost.
