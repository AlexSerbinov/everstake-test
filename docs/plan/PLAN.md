# План: компактний knowledge assistant із виміряною якістю

## Коротко: що робимо по черзі

1. **Спочатку якісно готуємо базу джерел.** Агенти широко шукають джерела понад seed CSV і мінімальні 200 документів, допомагають налаштувати crawler і перевірити текст, дати, таблиці та копії. Робимо лише потрібний для цього TypeScript-каркас і облік; чат та UI поки не будуємо.
2. **Фіксуємо початковий корпус.** Зберігаємо перевірений знімок `corpus-v1`, його склад, прогалини, походження документів і фактичні витрати підготовки. Це точка відліку якості даних.
3. **Продумуємо й перевіряємо оновлення.** На окремій копії знімка перевіряємо незмінну сторінку, виправлення, новий документ і збій. Код знаходить зміни; API використовується лише для потрібної модельної обробки й embeddings.
4. **Готуємо пошук і простий RAG baseline.** На зафіксованому корпусі будуємо пошук за словами та змістом, вимірюємо просту відповідь до додавання агентного циклу.
5. **Навчаємо асистента користуватись інструментами.** Знайти, дочитати, порахувати, відповісти. Без окремих правил для CEO, CMO чи конкретного продукту.
6. **Перевіряємо відповідь і показуємо Trust Score.** Видно джерела, перевірки, склад бала та фактичну ціну запиту.
7. **Порівнюємо з baseline.** Ті самі питання, зафіксовані дані, всі результати й витрати. Виправляємо причину помилки, а не конкретне формулювання питання.
8. **Готуємо живе демо й короткі документи.** Відразу видно таймер і кроки пошуку; після відповіді — джерела справа з датами та переходами від цитат. Можна додати джерело, змінити правило та пояснити результат наживо.

Це короткий маршрут; контракт evaluation готуємо на початку, а повне порівняння повторюємо наприкінці. Деталі папок і залежностей — у [ARCHITECTURE.md](ARCHITECTURE.md). Розбір попередніх рішень — у [DECISIONS.md](DECISIONS.md).

### Перший окремий результат — якісна база

Погоджене рішення від 2026-09-13: **етап A — Codex і субагенти досліджують джерела та готують корпус через наш TypeScript-код; етап B — застосунок сам оновлює його тим самим кодом.** Перший результат — маленький перевірений pipeline; далі corpus-v1, а не готовий асистент. Роботу агентів у межах наявної підписки використовуємо для дослідження, написання повторюваних скриптів і перевірки якості. Це план використання наявного доступу, не припущення про безлімітну чи гарантовано безкоштовну обробку.

Результат етапу: максимально повна база знайдених релевантних публічних джерел (≥200 документів — мінімум, не межа), із відомим походженням, точні знімки джерел, очищений текст зі структурою, окремі дати, групи копій, список втрат/пропусків і команда повторення збору. Перевірити вибірку з кожного типу джерела, всі виявлені збої extraction та складні випадки дат/таблиць. Зберегти кількість перевірених документів і висновки; не оголошувати весь корпус перевіреним за кількома прикладами.

Агенти можуть пропонувати виправлення extraction та пояснення, але їхні перекази не підміняють першоджерела. Кожне прийняте виправлення має посилання на snapshot/уривок і спосіб повторення. Не збираємо таблицю готових відповідей на evaluation. Початковий і майбутній API-шлях мають однаковий document contract і перевірки якості.

`corpus-v1` — **початковий знімок даних**. RAG/MCP/поточний Codex — **baseline систем відповідей**. Це різні результати: наявність хорошої бази ще не дає accuracy асистента. Якщо embeddings ще не побудовані, так і позначаємо; їхні токени та вартість вимірюються окремим index run.

Порядок: дослідження джерел субагентами → мінімальний CLI та облік → пробні 12–20 документів → QA й повторювані виправлення → широкий збір усіх знайдених релевантних джерел → corpus-v1 → контрольований refresh без Codex. Ролі субагентів, результати й перевірка переходу розписані в [CRAWLER.md](CRAWLER.md). Субагенти не створюють окремий runtime і не готують таблицю відповідей замість корпусу.

### Потім — оновлення вже підготовленої бази

Оновлення має працювати без ручного запуску coding-agent: перевірити HTTP/content → виділити нові/змінені документи → прогнати ті самі extraction/validation правила → переіндексувати змінене → опублікувати новий snapshot. Окремий LLM-виклик для кожної сторінки не обов'язковий; API потрібний для embeddings і лише тих задач extraction, для яких він виправданий вимірами.

Якщо початкове виправлення зробив агент і воно не відтворюється кодом, або перетворити його на загальне правило/перевірений API-крок, або явно позначити цей тип документа як такий, що потребує перевірки. Не дозволяти першому автоматичному refresh непомітно втратити якість ручної підготовки. Спершу один контрольований refresh із вимірами; розклад і частоту визначити після нього.

Покомітний план виконання — наступний окремий крок після узгодження цих етапів. Тоді розбити роботу на завершені зміни з перевірками та видимим результатом; історія відображатиме фактичну розробку з реальними timestamps, без ретроспективного створення штучних комітів.

## 1. Результат

Побудувати асистента, який відповідає лише з самостійно зібраного публічного корпусу. Фактична відповідь містить факт, дату та конкретне джерело. Історичний синтез показує зміни за кількома джерелами. Недостатні докази означають чесну відмову; збої інфраструктури мають окремий статус.

Критерії приймання — оригінальне завдання, особливо §3–5, §7–11. Менше коду має полегшити пояснення й зміну вимоги наживо, зберігаючи виміряну якість. Завдання очікує 6–8 годин: на кожному етапі перевіряти залишок обсягу, скорочувати додаткові можливості, чесно описувати незавершене. Це орієнтир обсягу, не обіцянка строку реалізації.

## 2. Що беремо з попередньої роботи

- Codex: зрозумілі частини crawler, дедуплікації, SQLite/FTS, embeddings, bounded document reading, числових перевірок і калькулятора.
- Claude: принцип єдиного ledger для всіх API-викликів, зв'язок із вимірами етапів, загальна сума витрат, деталізація запиту й автоматична генерація COST.md.
- Наявні базові й складні питання: регресійні набори, а не blind evaluation.
- Перевірені інженерні рішення адаптуємо; стара база, числові результати й витрати не стають результатами нової реалізації.

## 3. Компактна архітектура

Підготовка: конфіг джерел → discovery → fetch → extraction → sanitation → dedup → chunks/embeddings → SQLite.

Відповідь: питання → обмежений агент → search/read/calculate → submit → перевірки → Trust Score → відповідь і receipt.

Усі етапи та API-виклики пишуть у спільну систему вимірювання. UI і звіти читають її, а не ведуть власні лічильники.

Чотири інструменти агента:

1. `search(query, filters)` — пошук доказів у зафіксованому корпусі.
2. `read(document_id, section_or_offset)` — читання потрібного розділу й сусідніх уточнень; пов'язані документи доступні лише з індексу.
3. `calculate(expression, inputs)` — обмежена арифметика з джерелами операндів та явними припущеннями користувача; без довільного виконання коду.
4. `submit(answer, claims, sources, dates, status)` — структурована пропозиція відповіді, перевірена сервером.

Писати на **TypeScript** — це мова автора, на якій він має пояснювати й змінювати код наживо. Runtime — Node.js, сховище — SQLite; Gemini 3.x для генерації, OpenAI для embeddings. Python залишається лише джерелом ідей із попереднього Codex, не частиною нового runtime. Конкретні версії, ідентифікатори моделей, доступність і ціни перевірити перед реалізацією; зафіксувати їх у конфігурації та результатах запуску.

Сервіси — звичайні модулі одного застосунку: `crawler`, `indexer`, `search`, `answer`, `evidence`, `measurements`, `trust`, `evaluation`. Кожен має одну зрозумілу відповідальність, явні входи/виходи й тести поруч. Без окремих контейнерів, HTTP-запитів між ними або загального framework для агентів.

Код, назви, коментарі й повідомлення застосунку — простою англійською. План і пояснення автору — простою українською. Короткі функції з предметними назвами, явний потік даних, перевірки на зовнішніх межах, мінімум залежностей. Коментар пояснює причину рішення, а не переказує кожен рядок. Точні правила читабельності й приклади контрактів — у ARCHITECTURE.md.

### GitHub має пояснювати демо структурою

Кожний змістовний блок має очевидне місце. На сервері — папки сервісів; у браузері — `web/features/live-search`, `answer-sources`, `answer`, `verification`, `trust-score`, `costs`, `request-error` і форма питання. Живий пошук та фінальні джерела зберігаються окремо: перший показує процес, другі — докази відповіді.

Назви файлів пояснюють дію: `search-results.ts`, `source-cards.ts`, `elapsed-timer.ts`, `answer-question.ts`, `build-receipt.ts`. У кореневому README є карта «блок на екрані → папка → головна функція → тест», а всередині папки — короткий README з входом/виходом і поясненням відповідальності. Не ховати все в `app.ts`, `service.ts` чи `utils.ts`; водночас не дробити кожну кнопку на окрему архітектурну одиницю.

Під час створення кожного блока провести коротку репетицію: відкрити його на GitHub, пояснити потік даних, показати ключову функцію й змінити одну поведінку з тестом. За §9–10 потрібно пояснювати й змінювати код, тому читабельні блоки — спосіб цього досягти. Детальна карта з десятьма елементами демо й правила локалізації змін — у [ARCHITECTURE.md](ARCHITECTURE.md).

## 4. Загальні правила доказів

- Порівнювати той самий об'єкт, показник, одиниці, часовий період та умови.
- Розрізняти дату публікації, зміни сторінки, завантаження та чинності твердження. Невідома дата залишається невідомою; дату спостереження показувати з відповідною позначкою.
- Авторитет джерела залежить від предмета питання. Компанія підтверджує власну заяву, аудитор — висновок свого аудиту; це різні типи доказів.
- Враховувати явне виправлення або зміну чинності, а не просто найбільший timestamp.
- Дублікати не стають незалежним підтвердженням.
- Нерозв'язаний конфлікт показувати з прив'язкою до джерел; не вигадувати, яке перемогло.
- Розрахунок не встановлює договір, знижку, гарантію чи застосовність тарифу.
- Підтверджена часткова відповідь допустима, якщо прямо зазначити, які запитані факти невідомі.

Без правил `CEO → /about`, винятків під DORA чи назви продуктів. Конфіг описує джерела, а не правильні відповіді на eval.

CEO, CMO, COO й незнайома посада проходять один маршрут: знайти потрібну роль та організацію → прочитати твердження й дату чинності → зіставити релевантні джерела → відповісти або пояснити брак доказів. Закритого списку дозволених посад немає. Короткі структуровані твердження формуються лише для поточного питання з точними цитатами; глобальну онтологію фактів не будуємо.

## 5. Захисні межі

Інструкції, адресовані AI, очищаються перед індексацією; вилучені фрагменти обліковуються. Документи передаються як позначені дані. Інструменти не можуть писати назовні, виконувати команди або самовільно розширювати мережевий доступ. Посилання вирішує код за реєстром повернутих доказів.

Код перевіряє числові значення з одиницями, валютами й масштабом, арифметичні результати, походження дат, посилання та вимоги до історичного синтезу. Наявність числа у фрагменті не доводить правильності його семантичного використання: це перевіряє evaluation. Regex-фільтр не оголошувати універсальним захистом від injection.

Один evidence-сервіс обробляє всі шляхи читання: пошуковий уривок і повний документ мають однакові sanitation/serialization rules. Реєстр зберігає саме текст, реально показаний моделі; невидимий хвіст документа не може підтвердити число. Перевірки працюють за статусами й reason codes, а не за точним текстом фрази «не знаю».

## 6. Що свідомо не включаємо

Редактор ваг у UI, криптографічний ланцюжок аудиту, загальний ledger усіх фактів із автоматичними штрафами документам, people registry, конструктор freshness-політик, live MCP/HTTP у базовій відповіді. Зберігаємо простий evidence receipt із точним текстом доказів і хешами. Trust Score входить у базовий обсяг; його правила й ваги доступні у версійованому конфігураційному файлі.

MCP лишається обов'язковим об'єктом baseline-порівняння. YouTube включаємо: captions для відбору, Soniox для транскрипції прийнятих відео, Gemini 3.8 Flash для контекстної перевірки спікерів, датовані репліки й окремі витрати. Деталі — [YOUTUBE_PLAN.md](YOUTUBE_PLAN.md). Непідтримані PDF/зображення явно обліковувати; якщо вони потрібні для обов'язкових доказів, пріоритезувати extractor перед декоративними можливостями.

## 7. Послідовність реалізації

| Етап | Робота | Що доводить завершення |
|---|---|---|
| A1. Підготовка бази | Мінімальний TypeScript CLI, облік, discovery/extraction/dedup; дослідження й QA агентами | Є відтворюваний збір, документи та список проблем; API-виклики обліковані з першого |
| A2. Початковий snapshot | Перевірити якість і зафіксувати corpus-v1, manifest та прогалини; підготувати eval contract | ≥200 змістовних документів із provenance, звіт вибіркової перевірки, окремі витрати підготовки |
| B. Механізм оновлення | Перевірка змін, повторювана обробка, виміри API, безпечне оновлення snapshot | Контрольні no-change/change/new/failure сценарії не псують попередню базу; потреба ручної перевірки видима |
| C. Пошук і baseline | Побудувати виміряний індекс і simple-RAG baseline, підготувати MCP-порівняння; повторний старий Codex benchmark опційний | Є сирі відповіді, фактичні витрати та зафіксовані умови порівняння |
| D. Компактний агент | Додати bounded read/search і calculate | Виміряно, які складні питання покращилися та скільки це коштує |
| E. Загальні виправлення й Trust Score | Класифікувати провали, фіксити причини, перевіряти інші назви/числа; реалізувати пояснюваний score | Немає нових спеціальних правил під питання; повний повторний прогін із балами та аналізом упевнених помилок |
| F. Демонстрація й матеріали | Простий UI, COST/EVAL/REPORT/PROCESS, MCP-порівняння, запуск | Результат відтворюється, числа узгоджені, зміна джерела демонструється наживо |

Baseline на однаковому корпусі повторити після фінальних змін corpus/index: ранній результат не підмінює фінальне порівняння.

## 8. Мінімальний UI

Питання, відповідь, дата з поясненням її значення, клікабельні джерела, короткий trace. Для кожної підтриманої відповіді — Trust Score 0–100, кольоровий індикатор і розгорнуте пояснення внеску кожної складової з посиланням на докази. Для кожного запиту — фактичні API-витрати, токени, час і розгорнуті кроки. Окремий простий екран Cost: витрачено загалом, один build, один запит, evaluation, помилки/повтори, розбивка за моделями та запусками. Corpus: список джерел, стан збору, exclusions, останнє оновлення.

Trace показує реальні дії, а не приховані міркування моделі: що шукали → що знайшли → що відклали й чому → що прочитали → що процитували → які перевірки пройдено. Ці лічильники рахує сервер; браузер відображає. Відкинута чернетка доступна окремо з чіткою міткою, щоб її не сприйняли як відповідь.

**Обов'язково поєднати два референси:** Claude — загальний/покроковий таймер і нумеровані цитати з картками джерел справа; Codex — живі результати кожного пошуку з уривками, датами, новими/повторними знахідками та причинами відбору. До фіналу користувач бачить пошук, після фіналу — які докази стали цитатами. Дати джерел не приховуються: published/updated/fetched/effective мають різні позначки, невідоме показується явно. На mobile картки переходять під відповідь.

Під час довгого model call залишається правдивий статус і живий час, без фіктивних кроків. API error відображається окремо від «немає надійної відповіді», без «Verified evidence» чи «Why this answer passed». Детальний сценарій, контракт подій і перевірки — у [LIVE_EXPERIENCE.md](LIVE_EXPERIENCE.md).

### Trust Score: обов'язковий функціонал

Рішення користувача від 2026-09-13: включити Trust Score в нову реалізацію. Він пояснює якість наявних доказів; число 90 не означає 90% імовірності правильності.

Початкова формула — `round(100 × Σ(weight × component))`, компоненти в діапазоні 0–1, ваги сумарно 1. Початкові ваги нижче є гіпотезою дизайну, а не виміряною калібровкою:

| Складова | Вага | Що враховуємо |
|---|---:|---|
| Авторитет і відповідність джерела | 30% | Призначення джерела щодо конкретного твердження, походження, заявлені межі |
| Часова відповідність | 20% | Докази потрібного періоду, явна дата чинності; старе історичне джерело не штрафується за вік саме по собі |
| Покриття тверджень доказами | 30% | Зв'язки тверджень із точними уривками, результати числових/цитатних перевірок; технічне покриття не прирівнювати до semantic entailment |
| Узгодженість і незалежне підтвердження | 20% | Підтримка зіставних тверджень, відомі конфлікти, collapse дублікатів і синдикації; одна офіційна сторінка не означає автоматично ненадійну відповідь |

Розрахунок виконує звичайний код за evidence metadata, реєстром claim-to-source links і результатами gates; окремого LLM-виклику для бала немає. Якщо семантичні зв'язки чи конфлікт позначила модель, це явно вказується як model-derived input, а не незалежна перевірка. Самооцінку моделі в підсумковий бал не включати.

На етапі реалізації зафіксувати таблицю нормалізації кожної складової, обробку unknown і межі кольорових діапазонів до фінального evaluation. Невідомі дати чи незалежність джерел показувати явно й обробляти консервативно; відсутність знайденого конфлікту не є доказом згоди. Не запроваджувати глобальні штрафи документам за збіг назви показника.

Score не може обійти gates або перетворити відсутні докази на відповідь. Для повної відмови чи provider error повертати `trust: null` із причиною, а не 0. Для часткової відповіді бал стосується лише підтриманих тверджень; UI окремо показує непокриті частини питання. Нерозв'язаний матеріальний конфлікт завжди має видиму позначку, незалежно від середнього бала.

API, UI, receipt і evaluation використовують один результат: загальний бал, складові, ваги, внески, причини, unknown/conflict flags і версію scoring policy. Історичні бали зберігаються з тодішнім конфігом; перерахунок новою формулою створює окреме порівняння.

## 9. Критерії готовності

- Усі обов'язкові deliverables, включно з реальними agents/skills/prompts, REPORT на 2–3 сторінки й односторінковим PROCESS.
- Повний evaluation із ≥5 негативними питаннями та окремим числом випадків вигадування фактів.
- Ціль — повністю правильні відповіді на одному погодженому наборі з 20 питань (5 базового походження + 15 складних); це не гарантія результату. Порівняння з baseline виконується на цьому ж наборі, усі регресії розібрані.
- Нуль виявлених вигадок — ціль приймання; невирішені випадки явно показані, а не приховані загальним відсотком.
- Нова компанія/домен додається конфігурацією; числові й часові тести працюють на синтетичних інших даних.
- Початковий corpus-v1 має окремий звіт якості; автоматичне оновлення зберігає той самий контракт даних і явно позначає випадки, які не може обробити самостійно.
- CEO, CMO та нова роль обробляються тим самим кодом; заміна організації, ролі, URL і порядку джерел не потребує нової гілки логіки.
- Один TypeScript answer-service використовується API, CLI та основним evaluation; RAG baseline явно окремий режим із тим самим evidence/validation contract.
- Кожному блоку демо відповідає зрозуміла папка й головний файл; README веде від екрана до функції та тесту. Автор пройшов пояснення й невелику зміну кожного блока, а не лише огляд дерева папок.
- На повільному запиті UI відразу показує таймер, а результати пошуку надходять під час роботи; фінальні цитати ведуть до точних уривків із датами. Error state не містить позначок успішної перевірки.
- Загальні витрати включають експерименти й повтори. Ціна одного build належить одному відтворюваному запуску.
- Trust Score відображається з поясненням, має детерміновані тести та окрему перевірку зв'язку з correctness; високі бали помилкових відповідей не приховуються.
- Автор може пояснити й змінити код наживо. Історію розробки ведуть із реальними timestamps після окремого дозволу на Git-дії.

### Загальне правило для прикладу з CEO

Скріншот користувача — референс роботи з доказами, не таблиця правильної відповіді. На ньому оголошення має дату червня 2025, а поточні сторінки завантажені у вересні **2026**. Це не доводить точну дату зміни посади, повернення попереднього керівника або причину зміни. Не фіксувати ці імена чи дати в runtime.

1. Визначити, про яку організацію, властивість/роль і момент часу запитують. Це звичайна робота моделі в наявному answer loop, без нового окремого агента.
2. Знайти релевантні джерела; якщо вони розходяться, дочитати точні речення з ролями, датами й контекстом. URL із `/about` сам по собі не доводить актуальність чи авторитет.
3. Розділити дату оголошення, явно зазначену чинність факту, редакційне оновлення і час спостереження сторінки. Не створювати відсутню effective date з fetched_at.
4. Історичне призначення і поточний перелік ролей можуть описувати різні періоди. Дати поточний найкраще підтриманий факт із точною часовою межею, потім пояснити історичне джерело. Якщо межі невідомі — атрибутувати «сторінка, перевірена тоді-то, вказує…»; не вигадувати перехід.
5. Якщо зіставні авторитетні джерела досі суперечать одне одному, показати конфлікт і обмежити висновок. Не обирати за числом копій, не приховувати конфлікт високим Trust Score.

Однаковий шлях має працювати для CEO, CMO, CTO, продукту, сертифікації чи числового показника. Автоматичні gates перевіряють refs/дати/числа/структуру; повну семантичну правоту моделі вони не гарантують. Semantic evaluation перевіряє саме твердження й їхню відповідність уривкам.

Контрольна сім’я тестів: історичне оголошення + поточний перелік; два одночасні несумісні твердження; лише старе джерело; невідома дата; новіша сторінка без релевантного факту; десять копій старого оголошення; нова роль без доказу. Повторити зі зміненими назвами організації, ролі, URL і порядком результатів. Назви та еталони живуть тільки в eval fixtures. Це переносимі регресії, а не доказ універсальної точності.

### Комплект здачі та простий запуск

README має давати один зрозумілий шлях: встановити залежності → налаштувати ключі за `.env.example` → зібрати/відновити дозволений snapshot → індексувати → запустити → виконати eval. Жодної залежності від `claude-work`, `codex-work` чи особистих директорій автора. Перевірити шлях із чистої теки; старі артефакти можна переглянути без API, нову відповідь отримують через реальний запуск. Якщо потрібен хост, це окремий крок реалізації, а не вже зроблений деплой.

`agents/` містить реально завантажувану конфігурацію research agent; `prompts/` — його правила й evaluator prompt; `skills/` — інструкцію для coding-assistant викликати наявний CLI/API з прикладом. Skills не потребують нового runtime engine. Tool schema/handler лишаються в одному registry `answer/tools.ts`; не копіювати схеми у три місця.

REPORT на 2–3 сторінки: архітектура й причини → рішення для брудних даних → виміряна якість/ціна → один абзац MCP better/worse → свідомі cuts → що змінили б за місяць. Місячна перспектива: покращення extraction/coverage за результатами помилок, незалежний eval, експлуатаційні перевірки; ACL та приватні джерела лише якщо з’явиться такий реальний сценарій. Детальні логи й таблиці винести за посиланнями.

Часова межа оригіналу — 6–8 годин у вікні 5 календарних днів. Не заявляти її виконаною на підставі старої роботи. Додаткові складні питання — резерв для точкових регресій, а не обов’язкові 40 питань від компанії. Повний новий Codex benchmark можна відкласти з поясненням; обов’язковий 20Q і абзац про MCP залишаються. API-доступ відновлений зі слів користувача; це не результат нового smoke test чи підстава вважати всі майбутні виклики успішними.

### Part B: одна сторінка, без коду

As-is: керівник приблизно годину на тиждень збирає tracker, Slack і зустрічі. To-be: код за розкладом збирає зміни з дозволених джерел, перевіряє повноту й прибирає дублікати; модель готує чернетку з посиланнями, результатами, блокерами та невизначеністю; керівник виправляє пріоритети й затверджує звіт. Доставка відбувається після схвалення. Не створюємо ці інтеграції в Part A.

Три метрики: медіанний час перевірки/підготовки керівником за тиждень (поточний орієнтир близько 60 хв); частка тверджень чернетки, що потребували суттєвого виправлення; частка звітів, готових до строку з усіма очікуваними джерелами. Спершу замір baseline, потім пілот; цільові значення — гіпотези, не вигаданий результат.

Failure: Slack feed не оновився або pagination пропустила частину tracker. До генерації код перевіряє checkpoints, статуси API та очікуване покриття. Позначає неповноту, сповіщає відповідального, повторює без дублювання і пропонує ручне доповнення; не видає неповний звіт за готовий. Нуль нових подій може бути нормою, тому він сам по собі не є доказом збою. Розклад, збір, доступи, дедуп і доставка — звичайний код; вибір бізнес-пріоритету й остаточна відповідальність — людина.

### Репетиція захисту

Підготувати чотири короткі сценарії: walkthrough питання до джерела/receipt; зміна правила або нового джерела з функцією і тестом; невідоме наперед питання; Process Discovery. Для останнього з’ясувати рішення, заради якого потрібний звіт, хто його читає, де реально витрачається час, які винятки й втрати, хто схвалює, які доступи та як помітять помилку. Лише після цього обрати першу автоматизацію за користю, ризиком і можливістю виміру.

При збої API показати його чесно; збережений минулий run дозволений як явно датований приклад, не live-відповідь. Захист вимагає участі у відеодзвінку й можливості змінити код наживо. Готовий UI та знання назв папок цього не заміняють.
