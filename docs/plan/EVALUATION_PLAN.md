Для E01–E05 також написати коротке пояснення складності; використати ті самі поля картки, що для hard cases. Усі відомі питання — регресії, не blind set.

Один фінальний повний agent run = **20 відповідей**. Порівняння simple-RAG на тих самих 20 означає ще 20 відповідей, а автоматичний judge — окремі виклики й витрати. Це треба явно показувати в бюджеті, не називати всі порівняння «лише 20 викликами». Під час розробки — deterministic fixtures і вибіркові повтори лише провалених/зачеплених кейсів. Для фінального комплекту порівнювані повні runs виконати один раз на незмінних умовах; повторювати лише після суттєвих правок або збоїв. Ручне оцінювання всіх 20 за рубрикою дозволяє обійтися без платного judge, із записаними verdict і причинами. До запуску встановити budget cap; досягнення ліміту дає incomplete, не зелені пропуски. Непідтверджені pending charges консервативно резервувати; cap не гарантує точного обмеження рахунку при вже активному виклику.

## Простий порядок роботи

1. Підготувати `eval/questions.json` (20 основних) і окремий резерв кандидатів: ID, питання, категорії, difficultyReason, expectedBehavior, requiredClaims, forbiddenClaims, evidence references, as-of та revision. Окремий службовий manifest описує походження й hash набору. Еталони, пояснення складності та source hints не передаються answer-service й не індексуються crawler.
2. Перед прогоном перевірити потрібні джерела й повні уривки в snapshot. Missing URL не доводить відсутність факту в усьому корпусі. Негативні еталони перевірити на всьому зафіксованому корпусі. Невалідний еталон виправляється до freeze; прогалина ingestion залишається чесною проблемою системи.
3. Заморозити corpus/index, question set, prompts/policy, model IDs і judge rubric. Прогнати основні 20 питань через той самий `answerQuestion`, що використовує чат. Провести simple-RAG baseline на тому самому наборі й даних. Повторний старий Codex — додаткове порівняння, не умова цього етапу.
4. Зберегти actual answer, status, джерела й точні уривки, trace, формули, Trust, usage, вартість і час для кожного питання. Оцінити зміст незалежно від Trust; перевірити вручну partial/fail, суперечності judge і всі позначені вигадки.
5. Для провалу вказати підтверджену причину: ingestion → extraction/index → retrieval → reasoning → evidence validation → infrastructure. Якщо причину не встановлено, так і написати; фронтенд її не вгадує.
6. Виправляти загальну причину й додавати малий deterministic-тест. Для швидкої перевірки можна повторити одне питання з новим run ID. Перед заявою про фінальну якість — повтор основних 20 на фінальній версії; вибірковий rerun не переписує старий повний звіт.
7. З одного збереженого report object генерувати EVAL.md, JSON та дані екрана. Відкриття Evaluation лише читає результати й не витрачає API. Запуск повного набору на першому етапі — CLI; окрема платна кнопка в UI не потрібна.

## Оцінювання та перевірка самого evaluator

Стан виконання (`pending/running/completed/error/cancelled`) окремий від verdict (`correct/partial/wrong/correct_abstention/false_abstention/ungraded`). `inventedFact` — незалежна позначка з конкретним твердженням і причиною, а не лише один взаємовиключний verdict. Помилка judge означає ungraded, не wrong відповіді й не pass. Ручна переоцінка зберігає початковий verdict, автора/підставу й rubric version.

Strict accuracy = (correct + correct_abstention) / кількість запланованих питань набору. Partial не входить у strict success. Поруч завжди planned/completed/graded/errors/not-run; неповний прогін має позначку «не завершено» й не виглядає фінальною оцінкою. Для незавершеної оцінки invented count означає «виявлено серед N оцінених», не доведений нуль у всьому наборі. Показати false abstentions, invented cases, latency, answer cost та judge cost окремо. Фільтр UI не змінює загальний знаменник непомітно.

Перевірки до платного повного запуску:

- Валідність набору: унікальні ID, рівно 20 основних питань, ≥5 negative, refs існують, meaningful difficultyReason у кожного основного питання. Відсутність еталонів у production corpus і аргументах answer-service.
- На відомих відповідях evaluator розрізняє правильну відповідь, красиву неправильну з ключовими словами, вигадану точну дату, коректний обчислений результат із доказаними операндами, правильну відмову й API error. Жодного автоматичного pass лише через слово «не знаю».
- Підрахунок метрик на змішаному fixture: partial, error, ungraded і not-run не приховуються; answer/judge retries враховані без подвійної суми.
- Runner з підставним provider проходить interruption/resume, не дублює завершені attempts і не змішує snapshots; resume допустимий лише з незмінним manifest. Новий запуск/повтор відображає нову спробу.
- Інтеграційний smoke через реальний answer-service, потім повні measured runs. Підставний provider перевіряє механіку, але не якість відповідей моделі.

## Екран Evaluation

Окрема видима вкладка **Evaluation**. Зверху — один набір із 20 питань, обраний run, дата, corpus/set revision, модель і мітка завершеності. Короткі показники: успіхи з N, часткові, помилки, виявлені вигадки, час і витрати. Нижче — читабельні розгортані картки; фільтри за verdict і типом складності. Колір доповнює текст, не заміняє його.

Кожна картка:

1. ID, повне питання, категорія і текстовий verdict. **Одразу під питанням — «У чому складність»**, видимий без розгортання.
2. Коротко «Що перевіряємо»: обов’язкові висновки та чого не можна вигадувати.
3. «Очікувана відповідь» і «Відповідь системи» поруч на desktop, одна під одною на mobile. Для not-run показати відсутність відповіді, а не порожній зелений блок.
4. «Чому така оцінка»: які пункти виконані, що пропущено чи вигадано, джерело оцінки code/judge/human. Code gates і correctness показуються окремо.
5. Посилання на точні датовані джерела через наявний `answer-sources`; розгортані trace, Trust і receipt через наявні блоки. Усі прив’язані до збереженого run, не до сьогоднішньої live-сторінки.
6. За наявності сумісного baseline — його відповідь/оцінка/час/ціна в розгортаному порівнянні. «Немає порівнюваного запуску» замість вигаданого покращення. Перевіряти сумісність set/corpus/model/policy, явно зазначаючи відмінність engine.

Фронтенд не виставляє verdict і не звертається до моделі для пояснення складності. Read-only endpoints повертають список запусків і конкретний report; публічна відповідь не містить ключів, службових prompts чи приватних debug даних. Перегляд еталонів людиною дозволений; answer-service працює в окремому контексті й їх не отримує.

## Файли та критерії готовності

Backend лишається в `src/services/evaluation/`: `run-evaluation.ts`, `grade-answer.ts`, `run-baseline.ts`, `write-eval-report.ts`; додати `build-eval-report.ts` як єдиний агрегатор для Markdown/API та `run-evaluation.test.ts`. Не створювати другу evaluation-систему для UI.

Окремий зрозумілий блок `web/features/evaluation/`: `evaluation-page.ts` (run selector, summary, filters), `question-result-card.ts` (складність, відповіді, verdict, comparison), `evaluation-page.test.ts`, короткий README. Спільні source/trace/Trust/cost компоненти перевикористовуються. Публічний `EvaluationReport` contract відокремлений від закритих grading inputs.

Готово, коли основні 20 питань мають збережені нові результати й чесні verdict, baseline порівнюється на тих самих умовах, усі 20 карток основного набору пояснюють складність, EVAL.md/UI/JSON показують однакові числа. Непройдені питання видимі з причинами; ціль нуль вигадок не підміняється намальованим успіхом. UI перевірити на mixed-results fixture, довгому тексті/URL, mobile, клавіатурі, незавершеному run та помилці завантаження. Перезавантаження екрана не запускає платних викликів.
